# 软件工程安全防破解

## 目标与边界

对用户自有或明确授权的软件实施纵深防御：将授权与关键决策放在服务端，结合安全通信、防重放、在线心跳、发行签名、代码混淆/虚拟化、运行时完整性与平台加固，提高逆向和篡改成本。

- 客户端运行环境不可信；客户端校验、混淆和反调试不能替代服务端鉴权。
- 不承诺“无法逆向”“绝对安全”或“挡住99%的破解者”；用具体测试、覆盖率、误报与性能证据描述效果。
- 只处理被授权的应用、构建链和服务端。不得扩展到无关进程、他人软件、内核驱动或系统安全设置；不关闭杀毒、EDR、系统签名和权限保护。
- 安装/加载本Skill本身不修改软件。未指定项目时询问项目位置和目标平台，不猜测路径，不擅自寻找并批量改造其他项目。
- 遵守项目约束与工具审批。依赖采购、生产切换、强制下线、破坏兼容性或更换鉴权协议需明确说明影响并取得必要确认；可先完成不依赖这些决定的审计和测试。
- 禁止把密钥、令牌、凭据、客户数据写入日志、示例或报告；不从客户端提取真实用户秘密来做测试。

## 一、先审计，再实现

1. 确认执行设备、授权工作区、项目根目录、服务端归属、语言、构建工具、平台/架构、最低系统版本、发布渠道及源码/LLVM IR/发行二进制可用性。
2. 修改前读取适用的AGENTS.md、README、构建/部署说明、相关实现与测试；核对已有改动，不回滚用户成果。代码定位优先使用项目概览、符号和有界搜索。
3. 绘制信任边界：登录、令牌签发/刷新、心跳、敏感接口、授权状态、离线行为、密钥存储、更新与签名流程。
4. 用户问“我是不是已写了心跳”时，必须定位客户端定时发送、服务端接收/鉴权、超时处理及测试。区分仅TCP保活、WebSocket Ping/Pong、业务心跳、完整授权租约；仅出现heartbeat字符串不算实现证明。
5. 建立现状表：防护项、真实代码位置、现有行为、风险、拟修改项、验收方法、依赖/阻塞。没有运行证据时明确标为静态观察或待验证。
6. 先修复服务端越权、失效会话仍可用、重放和明文通信等实质漏洞，再增加客户端成本型防护。保留构建、回滚、兼容与故障诊断能力。

## 二、LLVM混淆与代码虚拟化

用户要求代码混淆和虚拟化时，必须区分并分别落实，不能用压缩、去符号或普通控制流混淆冒充虚拟化。

### 正确选择处理层

- PE、Mach-O、ELF等原生发行文件通常包含机器码，不是能直接交给LLVM编译器的LLVM字节码。LLVM方案通常从源码或受支持的LLVM IR进入，在代码生成前执行保护Pass，再生成原生二进制。
- 已编译原生二进制需专用二进制重写/虚拟化保护器，或经受支持的lifting流程重建IR。不得承诺可无损恢复任意程序、异常、ABI或所有第三方库。
- .NET IL、JVM/DEX、JavaScript/Wasm与原生机器码分开评估；不能假设一个LLVM工具适用于所有格式。浏览器代码不能当成可保密载体。
- 如果只有发行二进制且工具链不支持，明确报告阻塞，并提出获取源码/IR、使用有授权的专用保护器、隔离可保护模块等可检查选项，不伪造编译结果。

### 实施要求

1. 核实真实存在的工具、LLVM版本、插件接口、许可证、平台/架构和CI可用性；使用官方支持的参数，不编造某款“虚拟化编译器”、仓库或命令。不擅自下载并执行来源不明保护器。
2. 自定义LLVM虚拟化Pass必须真实生成自定义指令表示及解释执行/分发运行时，保持原有语义、调用约定、异常、线程与内存行为；普通分支改写不算代码虚拟化。不存在的实现应作为需开发和验证的工作，不宣称开关即用。
3. 以用户要求的全程序保护为覆盖目标，枚举应用自有模块、静态/动态链接边界、生成代码、第三方库、FFI、运行时和不可处理区域。对不受支持的部分逐项报告原因，不悄悄改成“只保护几个函数”。
4. 若全量虚拟化造成明显性能/兼容风险，提供全量与关键逻辑保护的测量对比，由用户确认范围调整。许可证校验、协议关键逻辑可优先保护，但关键授权仍由服务端决定。
5. Release可组合使用经验证的字符串处理、控制流/数据流混淆、符号裁剪、链接优化和平台硬化；这些只是补充，不能替代虚拟化。调试符号私有归档以支持崩溃定位。
6. 正确安排代码变换、基线清单和最终签名顺序。保护器不可破坏平台代码签名、公证、商店规则或更新链；每个版本维护自己的完整性基线。
7. 验证产物实际包含受保护表示/运行时及目标函数覆盖，检查是否意外包含未保护的副本、源码映射或秘密；对原版和保护版运行行为差分、性能、异常、线程与升级测试。

## 三、服务端权威与WebSocket心跳

### 服务端处理原则

- 授权、账号/设备会话、许可证状态、角色/资源权限、额度/计费、风控、撤销与关键业务决策尽可能放在服务端；所有敏感接口都独立校验，不信任客户端传入的isAdmin、isLicensed或登录成功布尔值。
- 将可安全迁移的核心规则和秘密移到服务端。UI、本地硬件访问、必要离线功能等仍可能留在客户端；评估时延、带宽、隐私、可用性和离线需求，不把用户本地数据无授权上传。
- 客户端只持有最小权限、短时凭证或签名授权租约。服务端对过期、撤销、无权或不满足在线策略的敏感请求拒绝处理；禁用客户端按钮不是安全边界。

### 心跳实施

1. 使用wss://，连接时验证会话及Origin（浏览器场景），限制消息大小/频率/连接数；禁止在URL查询串、日志或错误页泄露令牌。选择适合平台的安全握手认证方式。
2. 原生WebSocket可使用协议Ping/Pong检测链路；浏览器JavaScript不能直接发送协议级Ping，应实现应用层heartbeat/challenge消息。链路存活不等于授权有效。
3. 业务心跳至少绑定协议版本、会话标识、单调序列号与一次性挑战；服务端记录接收时间和会话状态，返回经认证的结果/短时租约。客户端自报时间不作为唯一信任依据。
4. 周期、超时、最大失联窗口和重连上限由配置与业务预算决定，加入合理抖动、指数退避与速率限制；不要无限重试或重复启动多个定时器。
5. 明确状态机：连接中→已鉴权→在线→失联宽限→受限/重新登录；令牌轮换、登出、吊销、重复连接、网络切换和服务端重启均可正确收敛。
6. 授权续期须绑定当前连接/会话挑战并防重放，不能仅凭缓存成功响应续命。服务端时间是租约依据；客户端可用单调时钟控制本地超时。
7. 处理移动端后台挂起、系统休眠、代理空闲断连、时钟漂移、弱网和离线需求。宽限期不能无限延长，也不能静默放开敏感操作。iOS/浏览器后台无法保证持续保活。
8. 先在测试/预发布验证超时与拒绝行为；没有用户授权，不直接改变生产超时导致大规模掉线。

## 四、加密通信与密钥管理

- 全链路使用HTTPS/WSS，优先TLS 1.3，在兼容需求下使用安全配置的TLS 1.2。校验主机名、证书链与有效期；禁止跳过校验、自动降级为明文或安装全局信任后门。
- TLS是首要保障；“混淆网络数据”不是加密。加密也不能替代身份认证、授权、防重放与输入验证。
- 应用层确需额外加密时，使用成熟库的AEAD，例如AES-GCM或ChaCha20-Poly1305；为每个密钥保证nonce唯一，认证协议版本/会话/请求标识等AAD，标签失败立即拒绝，禁止自行发明算法或使用ECB。
- AEAD nonce与业务一次性挑战用途不同，不混为一谈。AEAD nonce可明文传输；必须防止同一密钥复用nonce，并明确密钥轮换及进程重启的处理。
- 不在客户端硬编码共享主密钥，不把从JS/应用中可提取的常量称为秘密。会话密钥使用成熟认证协商；长期秘密存服务端KMS/密钥库，客户端必要凭据用平台安全存储。
- 证书/公钥固定只在合适的原生场景审慎启用，包含备用密钥、轮换和恢复方案，不破坏企业合法代理与更新能力。浏览器应用无法自定义浏览器TLS校验或可靠防止本地调试。

## 五、nonce、防重放与响应新鲜性

用户原文“Anons”按nonce（一次性随机数）理解，不冒充存在同名密码学标准。每次返回不同字符串不能防重放，必须同时校验认证、绑定、有效期和一次性消费。

1. 使用密码学安全随机数源生成足够强度的挑战，通常至少128位；挑战包含服务端截止时间与用途，并绑定当前会话、账号、请求标识和相关操作/请求体摘要。
2. 明确请求/响应信封，例如version、session_id、request_id、challenge_nonce、server_time、expires_at、result与认证信息。字段按选定的标准编码规范进行MAC/签名验证，防止歧义；不要自造不确定的JSON签名方式。
3. 浏览器/原生客户端仅接受属于当前待处理请求和当前会话的认证响应。验证预期挑战、请求关联、有效期与完整性后，原子消费一次；重复、跨会话、过期、字段被改写或未知请求一律拒绝。
4. 服务端存储并原子消费挑战/请求ID，配置TTL及容量限制，覆盖并发进程、重试、多实例和重启场景。需要幂等的业务使用独立幂等键和结果记录，拒绝重放不等于重复扣费。
5. 使用标准消息签名或受支持的认证协议；服务端私钥永不下发。客户端用于验签的公钥可以公开。若采用MAC，其共享密钥的可提取性和会话隔离风险必须说明。
6. 时间戳、TLS和签名各自都不能单独证明一次性；要有可信状态及绑定。收到签名但过期的“登录成功”仍应拒绝，服务端接口不能因为客户端显示已登录而放行。
7. 对离线许可证使用签名、有效期、版本和允许的功能范围，明确撤销/时间回滚能力的限制，不承诺客户端离线防重放绝对不可绕过。

## 六、反调试、模块注入与Hook/完整性

这些是应用自身的纵深防御，不是可信根。攻击者若控制客户端可篡改检测器及其结果；不得将客户端的“校验通过”报告作为服务端授权的唯一依据。

### 通用策略

- 将严格反调试/反篡改策略限制于发布构建，保留明确的开发与测试配置，但发行包不可通过普通环境变量、配置项或远程无认证开关绕过。
- 用受支持、可维护的平台机制检查应用自身。根据可信证据拒绝启动或停止受保护功能，撤销本地会话并通知服务端；安全关闭自身，不蓝屏、不干扰别的进程、不销毁用户文件、不无限崩溃重启。
- 结合签名、来源、版本、预期模块、完整性与多个信号判断。先测试系统组件、输入法、辅助功能、企业安全软件、覆盖层和合法插件兼容，不能把任意额外模块简单等同恶意注入。
- 确认异常模块/篡改后按已批准的严格发布策略拒绝启动或退出自身；单一不可靠信号应采用受限运行/重新认证等可解释策略，并报告误报边界。

### 各平台能力

| 平台 | 防护基线与必须说明的限制 |
| --- | --- |
| Windows | 发行文件/模块签名和可信发布源、受支持的加载限制、DEP/ASLR/CFG等编译/链接保护；检查自身调试状态及加载模块的路径、签名、版本和发布清单，处理WOW64、合法插件及合法安全组件。确认未授权DLL加载后安全终止自身。单看DLL文件名不足以识别注入，也不能保证发现无文件映射/手工映射。 |
| macOS | 代码签名、公证、Hardened Runtime与Library Validation等可用机制，最小化entitlements；评估自有进程调试/动态库完整性。不要关闭SIP或用禁用库验证换取表面兼容；合法插件需明确设计。 |
| iOS | 正式签名与发布渠道、沙箱、Keychain及适用的App Attest等服务端验证；考虑后台限制和商店规则。越狱/调试信号只是风险证据，不能保证完整探测或强制持续WebSocket。 |
| Android | 发行签名、R8及需要时的原生层保护、Keystore、应用完整性及适用的Play Integrity服务端验证；root/调试/注入信号可能被绕过，处理非GMS、不同商店与无网络场景。 |
| Linux | 发行包/更新签名、RELRO/PIE/NX等平台硬化、依赖及装载路径控制、最小权限与适用沙箱；根据发行方式检查自身代码与动态库，兼顾合法发行版库差异。root控制下不承诺可靠防调试。 |
| 浏览器 | 服务端鉴权、TLS、严格CSP、合适的SRI/Trusted Types、依赖/供应链和XSS防护。不能阻止用户打开开发者工具、读取JS/Wasm或像原生进程一样枚举DLL；混淆只增加成本。 |

### .text/代码段哈希与Hook检测

1. 识别格式、架构与可执行区：PE/ELF常见.text，Mach-O通常为__TEXT,__text；不是所有机器指令都在名为.text的单一节。明确覆盖代码、导入/间接调用表及其他区域的范围。
2. 以正确版本/架构的最终发行代码生成外置签名清单；包含构建ID、模块身份、算法、覆盖区间及有效策略。保护器和编译链接变换完成后再生成基线，按格式正确处理签名区域与自引用问题，并核验最终签名产物。
3. 通过安全通道获取且验证清单签名，清单密钥有轮换策略，校验版本绑定与新鲜性；不能接受攻击者控制的“预期哈希”，也不能为了通过校验自动信任本机当前字节。
4. 分别定义磁盘与内存测量规则。处理ASLR、重定位、导入修复、延迟绑定、热补丁、JIT、运行时解密/虚拟化及平台装载器行为；使用格式感知的规范化或稳定区间，不能盲目将磁盘.text原始哈希与内存直接比较。
5. 使用成熟哈希算法（如SHA-256）。完整性失败先确认是否为真实版本/架构匹配和合法装载变化，测试严格策略后按约定拒绝受保护操作或退出自身；更新版本必须提供对应基线。
6. 代码段哈希只能发现覆盖区间内的变化，不能保证检测IAT/GOT、虚表、数据指针、解释器状态或其他无代码修改的Hook，也存在检测间隔/TOCTOU风险。不得把“哈希没变”说成没有Hook。
7. 在授权的隔离测试环境验证自己的程序；不安装未经批准的注入驱动，不更改系统保护，不把反检测能力用于隐藏恶意行为。

## 七、工程落地与验收

- 小步修改：服务端认证与防重放→TLS/安全存储→业务心跳与租约→构建与签名→虚拟化/混淆→平台运行时完整性。若顺序因项目而调整，说明依赖。
- 对协议变更提供客户端/服务端版本协商、灰度、可审计回滚和明确失败行为，不能让老客户端静默获得绕过路径。
- 加入单元、集成、真实发行包与跨平台测试；详细用例见本Skill的references/acceptance-checklist.md，执行前读取相关条目。不得只测试Debug构建。
- 用测试账号、测试证书、隔离数据库与预发布服务执行篡改/过期/重放场景。记录证据，不上传真实凭据或修改生产授权记录来“证明有效”。
- 若工具缺失、源码不可得、商用许可不足、某平台不支持、生产不可访问或测试设备缺失，列出阻塞与待验证项，不把示例代码说成已经部署。

## 八、交付格式

最终交付至少包含：
1. 实际完成项及客户端/服务端/构建文件路径；现有心跳是否存在、证据在哪里、补了什么。
2. 各平台保护覆盖与明确例外；LLVM/虚拟化的真实工具、版本、覆盖率计算范围和产物证据。
3. 协议与密钥管理说明（无秘密值），重放拒绝、租约失效与兼容/轮换策略。
4. 测试命令/环境/结果、性能与误报观察；分别标明静态审计、本地实现、测试、构建、签名、部署和线上验证状态。
5. 剩余风险、阻塞、升级与回滚要求。客户端防护仅提高成本，服务端授权始终是安全边界。

当用户只要求创建或安装本Skill时，仅完成Skill文档、安装和加载校验，不宣称已经实现上述任一软件防护。
